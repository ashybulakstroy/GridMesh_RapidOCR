# Идея: убрать лишнюю работу из двух медленных этапов OCR

**Статус:** предложение для независимого ревью. Код проекта не изменялся.
**Дата замеров:** 2026-11-19.
**Проект:** `C:\Work\Projects\Prj_18_OCR_2`.
**Эталонное задание:** `data/output/0251327d5d384287926c40adfb259768` (фото 899×1599).

---

## TL;DR

Две медленные операции — это не «тяжёлые алгоритмы сами по себе», а два случая
**лишней работы**, которую можно убрать локально:

1. **«Поиск физической сетки» (~1,2 с).** Основной детектор AutoGrid находит
   10 вертикалей, а `build_grid` принимает только 5–9. Результат отбрасывается,
   и запускается резервный Physical Grid Graph V3. Тот сначала полностью
   прогоняет ещё и V2 (результат V2 на эталонном кадре оказался `REJECTED` и не
   использован), затем дважды запускает LSD по всей фотографии и долго фитит
   кандидатов. Одно фото последовательно обрабатывают три детектора.

2. **«Распознавание напечатанного итога» (~1,1–1,8 с).** Дешёвое чтение одной
   строкой (`read_line`, только распознаватель) даёт правильное число, но не
   проходит условия приёмки (уверенность 0,885 < 0,93, а сумма строк не
   сходится). Тогда вызывается `read_full` (детектор + распознаватель).
   Детектор RapidOCR из-за настройки `Det.limit_type='min'`,
   `limit_side_len=736` растягивает полоску 495×100 до **3648×736** (2,68 Мпикс).
   Один только детектор занимает ~1,03 с; распознавание — ~37 мс.

**Основное предложение:** дать распознаванию итога отдельный профиль детектора
без принудительного увеличения короткой полосы и не запускать дорогой V2, когда
резервный детектор и так уверенно нашёл сетку. На эталонном задании это должно
сократить общее время примерно с **3,19 с до ~1,8 с** (оценка), а на заданиях,
где медленный только итог, — на **1,0–1,7 с**.

Важно: в общем случае V2 не всегда «выбрасывается» — она участвует в выборе
итоговой сетки (см. §5.2), поэтому её отключение требует проверки на корпусе.
Это учтено в предложении.

Сервер обрабатывает задания по одному (`processing = Lock()` в
`App/web_server.py`), поэтому задержка этапа напрямую задерживает пользователя.

Замеры делались двумя способами:

   `data/output/<job>/performance_profile.json`,

Окружение: Python 3.14, `.venv` проекта, `OCR_ONNX_THREADS=2`,

Ограничение замеров: это одна и та же фотография и несколько соседних заданий;

### 2.3. Почему включается резервный путь

Код `App/geometry/service.py:42-73`:

```python
data, report = detect_for_lab(image)          # AutoGrid
...
if data is None or not 5 <= len(data['vertical']) <= 9 or len(data['horizontal']) < 3:
    physical, physical_report = detect_physical_graph(image)   # V3
    ...
```

На эталонном фото AutoGrid вернул `autogrid_vertical_count = 10` (см.
`receipt.json`), поэтому весь результат AutoGrid отбрасывается, и запускается
V3. Это не ошибка условия как такового — 10 вертикалей действительно нельзя
использовать как 5 границ четырёх колонок. Вопрос в том, что резервный путь
слишком дорогой.

Внутри V3 (`App/geometry/geometry_lab/physical_grid_graph_v3.py:84-88`):

```python
def detect_physical_graph(image):
    baseline, previous = v2(image)            # сначала всегда полностью V2
    gray = cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)
    response, dark = ridge_response(gray)
    parts = multiscale_segments(gray)         # LSD на scale 1.0 и 1.5
    vertical = fit_segments(parts['v'], 'v', (H, W))
    horizontal = fit_segments(parts['h'], 'h', (H, W))
```

Дополнительно:

- `multiscale_segments` (`physical_grid_graph_v3.py:16-34`) дважды запускает
  LSD по всему изображению. На 1,5× это ~3,2 Мпикс даже для фото 899×1599.
- `fit_segments` (`physical_grid_graph_v3.py:37-52`) для 61 вертикального и
  13 горизонтальных кандидатов строит плотные массивы точек и делает 4
  итерации робастного `lstsq` на каждый кандидат.
- Если фото горизонтальное, `App/pipeline.py:80-82` дополнительно прогоняет
  весь `build_grid` для двух поворотов на 90°, то есть резервный путь может
  выполниться дважды.

## 3. Диагноз №2: «Распознавание напечатанного итога»

### 3.1. Два режима

В том же эталоне этап занял **1136,9 мс**. В быстрых заданиях — **22–78 мс**.

Код `App/pipeline.py:200-273` устроен так:

1. Сначала дешёвые попытки `read_line` (только распознаватель, без детектора):
   - прямая полоса (`pipeline.py:227`);
   - две компактные полосы (`pipeline.py:242-263`).
2. Если ни одна не принята — `read_total(1)` вызывает `read_full`, то есть
   **детектор + распознаватель** (`pipeline.py:264-266`).
3. Если итог не найден или его уверенность < 0,85 при несовпадении суммы —
   `read_total(2)` повторяет то же самое с увеличением ×2
   (`pipeline.py:269-273`).

### 3.2. Почему дешёвые попытки не принимаются

Условия приёмки прямой полосы (`pipeline.py:235-237`):

```python
if (candidate is not None and (direct['confidence'] >= .93 or
        (direct['confidence'] >= .8 and all(r['line_total'] is not None for r in rows)
         and abs(current_sum-candidate) <= Decimal('0.01')))):
```

На эталоне:

- прямая полоса распознала `46864,00` с уверенностью **0,8847** — ниже 0,93;
- сумма строк не совпала: `computed_total = 534572800`, `total = 46864.00`;
- компактные попытки дали `46864.00` (0,888) и `4686400` (0,685).

`computed_total` получился огромным потому, что сетка V3 нашла только 3
горизонтали — всего одну товарную строку; количество и цена этой строки
перемножились в 534 572 800. То есть **дорогой OCR итога вызван не сложностью
итога, а неполной/неверной сеткой строк**.

Похожие примеры из пачки:

- `3e9b1c14`: строки 1 и 3 с пустым `quantity`, `computed_total = 40028` против
  `18650` → итог 1689 мс.
- `4699c8a7`: `math_match = true` → итог 22 мс.
- `0251327d`: одна строка, сумма не сходится → итог 1137 мс.

### 3.3. Почему `read_full` стоит целую секунду

Профиль детектора и распознавателя (эталонный кроп 495×100):

| Операция | Время |
|---|---:|
| `read_full`, первый вызов после прогрева | 1045–1379 мс |
| — детектор (3 прогона) | **1026,7 / 1032,3 / 1035,2 мс** |
| — распознавание найденных строк | 37,4–41,1 мс |
| Вход детектора (N,C,H,W) | **(1, 3, 736, 3648)** = 2 684 928 пикселей |

Причина — настройка RapidOCR в `rapidocr/config.yaml:130-142`:
`Det.limit_type: min`, `Det.limit_side_len: 736`, и реализация
`rapidocr/ch_ppocr_det/utils.py:76-111`: если короткая сторона меньше 736,
изображение **увеличивается** до 736 по короткой стороне. Для полосы 495×100
это коэффициент 7,36 → 3648×736. Детектор обрабатывает почти в 55 раз больше
пикселей, чем есть в исходной полосе.

Проект не задаёт `Det.limit_type` в `App/ocr/engine.py:15-32`, поэтому
действует библиотечное значение по умолчанию.

### 3.4. Проверка альтернативного профиля детектора

В отдельном процессе для той же полосы был создан RapidOCR с теми же
параметрами, но `Det.limit_type='max'`, `Det.limit_side_len=736`:

| Параметр | Текущий профиль | `limit_type='max'` |
|---|---:|---:|
| Вход детектора | 736×3648 | **96×480** |
| `read_full`, 3 прогона | 1026–1035 мс (только детектор) | **28,0 / 28,1 / 28,8 мс** |
| Результат | `46` + `864,00`, confidence 0,949 | `46 864,00T`, confidence 0,896 |
| `parse_number` | 46864.00 | **46864.00** |

То есть на этом кропе нативное разрешение достаточно: итог читается,
`parse_number('46 864,00T')` возвращает `Decimal('46864.00')` (проверено
отдельно). Это не доказывает, что профиль подходит для всех фото — это
доказательство того, что секунда не является необходимой ценой за детекцию
именно этой полосы.

Замечание: в эксперименте использовался лимит 736. Для рабочего варианта
разумно взять больший предел (например, 1280–2000), чтобы не уменьшать
крупные полосы; на данном кропе результат будет тем же (нативный размер),
но это нужно замерить.

## 4. Связь двух проблем

Цепочка на проблемных фото:

```
AutoGrid не принят → V3 находит мало горизонталей
        → строк мало/есть пустые quantity
        → сумма строк не сходится с итогом
        → дешёвое чтение итога не проходит приёмку
        → read_full с растягиванием полосы
        → +1,0…1,7 с
```

Поэтому исправление одного только итога ускорит задания с несовпадением суммы,
но не исправит качество строк. Исправление одного только V2/V3 ускорит сетку,
но на фото с пустыми ячейками итог всё равно пойдёт в тяжёлый путь. Нужны оба
направления, но начинать лучше с самого локального и измеримого — профиля
детектора для итога.

## 5. Предлагаемое решение

### 5.1. Идея A (основная): отдельный профиль детектора для короткой полосы итога

**Суть.** Не менять логику приёмки и не убирать детектор как источник
независимого свидетельства. Оставить `read_full` для итога, но дать ему
детектор, который **не увеличивает** короткую широкую полосу без нужды.

**Почему это правильное место для изменения.**

- Проблема локализована: `read_total()` — единственное место, где детектор
  применяется к заведомо одной-двум строкам внизу чека.
- Это не меняет пороги уверенности, предупреждения, арифметику и политику
  «не придумывать числа».
- На эталоне это убирает ~1,0 с из 1,14 с этапа; на других заданиях с
  медленным итогом — 1,3–1,8 с.
- Детектор остаётся: если альтернативный профиль не найдёт строки, можно
  откатиться на текущий.

**Варианты реализации (от простого к сложному):**

1. **A1. Отдельный экземпляр RapidOCR для строк.**
   В `App/ocr/engine.py` добавить ленивый `line_engine()` с теми же
   `Rec`-параметрами, но с `Det.limit_type='max'` и разумным
   `Det.limit_side_len` (например, 1280–2000). В `read_full` добавить
   необязательный параметр `line_mode=False`; `read_total` вызывает
   `read_full(sample, line_mode=True)`.
   - Плюс: не затрагивает заголовки/ячейки, которые используют обычный
     `read_full`.
   - Минус: второй ONNX-сеанс детектора — дополнительная память. Нужно
     измерить RSS; при необходимости инициализировать только детектор,
     а распознавание брать из основного движка.
2. **A2. Глобально переключить `Det.limit_type` на `max`.**
   Проще всего, но влияет на все вызовы `read_full` (заголовки, многострочные
   ячейки). Требует полного регрессионного прогона; при ухудшении — откат.
3. **A3. Временно подменять `text_det.preprocess_op` под существующим
   `_lock`.**
   Экономит память, но завязывается на приватный атрибут библиотеки; сложнее
   сопровождать. Не рекомендую как первый шаг.

**Ожидаемый эффект.** На эталоне: `read_full` 1,05 с → ~0,03–0,1 с;
этап итога 1,14 с → ~0,08–0,15 с. На заданиях с итогом 1,7–1,8 с — экономия
до ~1,7 с. Оценка, не гарантия: окончательные цифры зависят от корпуса и
выбранного лимита.

**Риски и как их закрыть.**

- Мелкий текст может детектироваться хуже, если детектор уменьшает крупные
  полосы. Поэтому лимит `max` нужно подобрать так, чтобы типичные полосы
  оставались в нативном размере; проверить на всех тестовых чеках.
- Меняется структура `footer_ocr` (одна строка вместо двух), хотя итоговое
  число должно остаться тем же. Сравнивать нужно `total`, `math_match`,
  предупреждения и `parse_number`, а не точные bbox.
- Второй экземпляр модели добавляет память. Измерить до/после; при
  неприемлемом росте использовать вариант с общим rec-движком.
- Первый вызов после старта сервера может включать загрузку модели; при
  необходимости прогреть движок при старте или при первом задании.

### 5.2. Идея B (следующая): не запускать V2, когда V3 уже дала уверенную сетку

**Суть.** V2 в начале V3 нужна не всегда. На эталонном кадре V2 вернула
`REJECTED`, то есть 307 мс были потрачены впустую. Но в общем случае V2
участвует в выборе: `physical_grid_graph_v3.py:168-169` сравнивает число
горизонталей V3 и V2 и может предпочесть V2. Поэтому нельзя просто объявить
«V2 всегда ленивая» без изменения поведения.

**Предлагаемый безопасный эксперимент.**

- Сначала выполнить V3.
- Если V3 нашла 5 вертикалей и достаточно горизонталей (порог подобрать,
  например ≥3 или ≥4), **не запускать V2**; вернуть результат V3.
- Иначе запустить V2 и применить текущее сравнение/откат.
- На эталоне это должно дать тот же результат, что сейчас (V2 была REJECTED),
  и сэкономить ~0,3 с.
- На корпусе сравнить `method`, число строк, `total`, `computed_total`,
  `math_match` и предупреждения. Если хотя бы одно задание меняет результат,
  порог/правило нужно скорректировать или отказаться от идеи.

**Альтернатива без изменения поведения:** оптимизировать сам V2
(например, переиспользовать `gray`/CLAHE и наблюдения, которые уже считает
V3) или запускать V2 и V3 параллельно. Параллельный запуск может дать
выигрыш по wall-clock, но усложняет диагностику и может конкурировать за CPU;
это отдельный эксперимент.

**Ожидаемый эффект:** до ~0,3–0,4 с на каждом задании, где V3 побеждает без
V2. Риск средний, потому что правило выбора меняется; обязательна проверка
на корпусе.

### 5.3. Идея C (потом): удешевить мультимасштабный поиск V3

Измеренные компоненты V3: `multiscale_segments` 326 мс, `fit_segments` 237 мс.
Варианты:

- запускать масштаб 1,5× только если после масштаба 1,0 не хватает
  вертикалей/горизонталей;
- ограничить поиск областью предполагаемой таблицы, а не всем фото;
- уменьшить плотность точек при фитинге длинных сегментов (сейчас шаг ~8 px);
  сократить число итераций робастного `lstsq` для «чистых» групп;
- переиспользовать CLAHE/серое изображение между V2 и V3.

Потенциал: ~0,2–0,4 с на резервном пути. Риск выше: меняется набор
наблюдений и, следовательно, координаты сетки. Это отдельный этап после A+B,
с обязательным сравнением качества на корпусе.

### 5.4. Идея D (качество, отдельный проект): не отбрасывать AutoGrid целиком

Сейчас при 10 вертикалях AutoGrid полностью отбрасывается, хотя его
горизонтали могли бы быть полезны. Возможные направления:

- исследовать, почему AutoGrid даёт 10 вертикалей (дубликаты/лишние края),
  и отфильтровывать лишние;
- комбинировать вертикали V3 с горизонталями AutoGrid;
- улучшить выбор горизонталей в V3, чтобы строк было больше и суммы сходились.

Это может убрать и медленную геометрию, и медленный итог (через корректные
строки), но это уже изменение качества распознавания, а не чистая
оптимизация. Нужен отдельный корпус и ручная проверка.

### 5.5. Идея E (альтернатива для итога): принимать согласие дешёвых чтений

Прямая и компактная попытки уже дали одно и то же число `46864.00`. Можно
принимать итог, если две независимые дешёвые попытки дали одинаковый
`parse_number` при уверенности ≥0,80, даже если сумма строк не сошлась,
и добавлять предупреждение о несовпадении. Это уберёт детектор на части
заданий без изменения его настроек.

Но это **продуктовое решение**: можно принять неверный итог, если OCR
дважды ошибся одинаково. Поэтому A предпочтительнее: она сохраняет детектор
как независимую проверку, просто делает его дешёвым. E можно рассматривать
как второй эшелон или как временную меру.

## 7. План проверки и критерии приёмки

### 7.1. Корпус

- `App/tests/*.jpg`, `*.png` (там уже есть несколько чеков);
- сохранённые `data/output/*/input.bin` (реальные задания);
- отдельно — фото, на которых сейчас включается резервная сетка и/или
  медленный итог (например, `0251327d`, `3e9b1c14`, `4699c8a7`, `6d4769a0`).

### 7.2. Что сравнивать

Для каждого фото — результат до и после:

- `geometry.method`, число вертикалей/горизонталей, число строк;
- `rows[*].cells[*].text` (или хотя бы количество/цена/итог);
- `total`, `computed_total`, `math_match`, `vat`;
- `geometry.warnings`, `numeric_issues`;
- `footer_ocr_attempts` (какие стратегии запускались);
- время фаз из `performance_profile.json`.

### 7.3. Критерии приёмки

- **A:** на всех фото `parse_number(total)` совпадает с текущим; `math_match`
  не ухудшается; предупреждения не исчезают; этап итога на проблемных
  заданиях ≤ ~150 мс (p95), на быстрых — не хуже.
- **B:** результаты (кроме таймингов/аудита) идентичны текущим на корпусе;
  если есть изменения — они должны быть объяснимы и не ухудшать метрики.
- **C:** допускаются изменения координат, но не должно быть новых ошибочных
  итогов; сравнение с текущим по качеству строк.
- Общий p95 времени задания должен снизиться; медиана не должна вырасти.

### 7.4. Тесты

- `pytest` по `App/tests` (в проекте есть `requirements-test.txt`,
  `pytest`, `pytest-xdist`);
- `node App/tests/browser_check.cjs` после `npm install --prefix App/tests`
  (см. README);
- отдельный прогон всех тестовых изображений через `pipeline.process()`.

## 8. Что предлагается НЕ делать

- Не ослаблять пороги уверенности и не удалять предупреждения ради скорости.
- Не вычислять итог арифметикой строк вместо OCR: это уже запрещено политикой
  проекта.
- Не увеличивать число потоков ONNX/OpenCV как основной способ: геометрия
  и так занимает ~1 ядро, а детектор итога — ~2,5 ядра; проблема в 55-кратном
  объёме пикселей, а не в нехватке потоков.
- Не кэшировать сетку между заданиями: входные фото разные.
- Не запускать задания параллельно в обход `processing = Lock()`: это
  изменит семантику «одно задание одновременно» и может ухудшить latency.

## 12. Итог для ревьюера

Предлагается не переписывать OCR, а убрать два доказанных источника лишней
работы:

1. **не растягивать короткую полосу итога** перед детектором (профиль
   `limit_type='max'` для footer);
2. **не запускать V2**, когда V3 уже дала достаточно подтверждённую сетку
   (с проверкой на корпусе).

Обе идеи локальны, измеримы и не меняют политику «не придумывать числа».
Наиболее спорный пункт — B, потому что V2 участвует в выборе сетки; именно
поэтому он вынесен на проверку после A. Идеи C–E описаны как возможные
следующие шаги, но не обязательны для первого улучшения.
